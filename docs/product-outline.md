# 全新生活助手产品大纲 · 讨论稿 v3

更新日期：2026-10-06。产品名待定。本稿属于设计文档，不表示功能已经实现。

## 1. 产品目标

打造手机端、以 GPT 娘为主角的生活助手，将随手备忘、日期安排、事项提醒、音乐闹钟和长期资料参考整合为一个入口。当前范围为 Android 手机，优先验证用户使用的 HyperOS 设备。

用户说一句话就能记录和安排事情。信息不足时，助手提出具体问题；已有信息足够时，直接执行并提供撤销。适用于工作、学习、生活、兴趣和个人项目，不限定考研。

这是独立的新产品。FocusPlan 参考事项与助手经验，青铃参考闹钟能力，GPT 娘素材参考角色。页面、数据模型和操作流程重新设计。

## 2. 核心体验

### 2.1 一句话办事

- “明天记得买牛奶。”→ 明日待办，无具体时间，不自动加闹钟。
- “明早七点用音乐叫我起床。”→ 创建七点音乐闹钟。
- “周五前交报告，帮我安排一下。”→ 保存周五截止要求，建议一个准备日期。
- “先写方案，再发给客户。”→ 保留先后关系，不捏造时间。
- “想看这部动画，先记着。”→ 备忘。
- “把刚才那件事挪到周日。”→ 使用当前上下文确定事项，改期并提供撤销。

### 2.2 真实的交互感

助手有承接上下文的能力：“晚一点”“第二个”“跟上次一样”可以接续当前问题或事项卡片。

示例：

用户：“明早叫我起床。”

GPT 娘：“铭哥，明早几点叫你？”如果已有确认的起床偏好，附带“按平时的 7:30”和“换个时间”。没有依据时不编造选项。

用户：“八点，别外放。”

GPT 娘：确认耳机模式含义。如果已有明确的“仅耳机，无耳机则振动”偏好，执行；否则问“没连耳机时改为振动，可以吗？”

执行成功后：“明早 8:00，耳机音乐闹钟；没连耳机时振动。”附带编辑、试听、撤销。

表情在提问、等待回答、执行完成时变化，但回复不需要每句都加语气词或长篇角色表演。

### 2.3 日常完整链路

快速输入 → 理解事项 → 检查必要信息 → 必要时追问 → 本地校验与执行 → 显示结果卡片 → 撤销或继续修改。

能通过当前上下文确定时，不让用户重复描述。复杂操作允许预览后确认；简单而明确的操作直接完成。

## 3. 页面与入口

### 今天

显示下一次闹钟、明确时间的事项、今日弹性待办、待处理的逾期事项。点击卡片可完成、改期或调整提醒。

### 日历

月历与周历显示事项标记，选择日期查看有序列表。支持日期、上午／下午／晚上、精确时间，不强制时间轴。

### 备忘

存放未定日期的事情、清单和想法。支持搜索、置顶、一键安排到日期。备忘与资料库分别管理：前者是待处理内容，后者是可长期查证的信息。

### 闹钟

管理独立闹钟、重复规则、音乐、试听、音频输出方式、稍后提醒和调度状态。事项关联提醒也能从此处查看，但停止响铃不等于完成事项。

### 资料与记忆

从头像／侧边菜单进入，包含“资料库”“我的偏好”“学习中的习惯”“学习设置”。不增加常驻主导航页。

### GPT 娘全局入口

任何页面都能点击角色输入，支持文字、后续语音输入、系统分享和桌面小组件。对话以短回复和事项卡片为主。

## 4. 时间与事项规则

事项只有标题也能保存。可选字段包括安排日期、时段、具体时间、截止要求、提醒、重复、标签和前后关系。

- 安排时间是“准备什么时候做”；截止要求是“最晚什么时候完成”，两者独立。
- 精确时间按时间排列；弹性事项按时段和手动顺序排列。
- “这周”“周末”“有空”可以作为弹性范围，不能自动变成某个精确时间。
- 没有时长就不假设占用一小时；只对明确的时间段做冲突校验。
- 只有一个时间点时，可以提示同一时刻存在其他事项，不能断言整段日程冲突。
- “先 A 再 B”支持简单依赖，不在首版扩展成复杂项目管理。
- 逾期事项等待用户补做、延期或取消，不自动无限滚动到明天。
- 重复事项按次保存完成状态；修改某一次和修改整个系列分别处理。
- 日期按用户当前设备时区计算；跨时区与本地钟点的含义由程序明确记录。

## 5. 主动询问机制

### 必须问的情况

1. 缺少执行必要字段，例如闹钟没有准确时间。
2. 匹配到多个可能目标，例如两件同名“开会”。
3. 新指令与当前关键约束相矛盾，例如要求仅耳机播放，又明确要求无耳机也要出声。
4. 无依据的推断会改变承诺，例如把截止日自动向后移。
5. 修改重复系列但范围不明确。
6. 从观察推测出长期习惯，准备将其用于默认安排。

### 可以先办的情况

1. “明天买牛奶”可保存明日待办，无需询问具体几点。
2. “记一下想换键盘”可保存备忘，无需分类。
3. 用户准确指定事项和新日期，可直接改期。
4. 已确认偏好能补全字段，且没有冲突，可以使用并在结果中说明。
5. 需要调研的其他信息不影响当前记录，可以先保存，不用阻断。

### 提问交互

- 每轮聚焦一个关键问题，默认 2–3 个有依据的选项，始终允许自由输入。
- “还没想好”可保存为待安排，不擅自设置提醒或闹钟。
- 回答后继续当前操作，避免重新走流程。
- 等待回答不妨碍其他事项录入；待解决问题以卡片保留。
- 超时未答不视为同意。切换话题时保留草稿，必要时通过卡片恢复。
- “嗯”“好的”只承接当前明确的问题或方案，不能扩展成其他操作的授权。
- 问题绑定待执行事项；回答时若目标已变化，重新核对，不把回答套到另一件事上。

## 6. 资料库：长期查证与参考

### 首版导入

文本、Markdown、粘贴内容。网页首版可保存链接和用户粘贴的正文，后续再增加受控抓取、PDF、Word、图片 OCR 与日历文件。

典型内容：课表、工作安排、项目说明、个人作息、既有计划、兴趣清单、操作笔记。

### 导入流程

选择／粘贴 → 显示解析结果与来源 → 用户确认保存 → 建立索引 → 可选提取偏好候选 → 用户选择是否采用。

导入资料不会自动创建里面提到的全部闹钟和任务，也不会直接覆盖个人偏好。批量采用资料中的安排时，先生成可编辑预览。

### 每份资料的信息

- 名称、来源、导入时间、版本。
- 内容适用的开始／结束日期，可为空。
- 可靠性由用户设定，无法判断时标注“未确认”。
- 是否允许用于助手回答、是否允许发送给远程模型。
- 原文、解析文本、索引，以及由它产生的记忆关联。

### 检索与引用

助手只读取与当前请求有关的片段。回答带简短来源，例如“根据你导入的《本学期课表》”。旧版本、过期课表和用户更正的资料要明确标识。

查不到时说明缺少信息并询问，不编造答案。“课表显示下午有课”是来源事实；“那我建议上午买东西”是助手建议，界面分开显示。

### 修改与删除

支持更新资料、停用、删除及清理索引。删除资料时显示关联记忆数量，可同时删除由它派生的记忆；保留的记忆标注原来源已删除，不能继续伪装成可查证事实。

检索片段、网页正文、聊天导入内容均作为资料处理，里面的指令不能改变助手规则或触发操作。

## 7. 长期记忆与习惯学习

### 三类长期信息

| 类别 | 例子 | 写入条件 |
| --- | --- | --- |
| 明确偏好 | “以后工作日都七点半叫我” | 用户明确要求，保存后通知并可撤销 |
| 资料事实 | 课表中周二 14:00 有课 | 保留来源、版本和适用期限 |
| 习惯候选 | 健身多次被移到晚上 | 程序统计提出候选，经用户确认才能作为默认偏好 |

### 观察范围

仅在用户开启“习惯学习”后，统计本应用内必要的操作：用户选的时间、改期、稍后提醒、取消，以及用户主动记录的完成时间。

不把“勾选完成的时间”当成实际开始时间；不把未打开应用或未勾选当成没有做。删除、取消也不能自动解释为用户讨厌该活动。

不需要读取其他应用、监听全局输入或监控位置来建立首版习惯功能。

### 候选产生

首版可使用可解释的简单统计。示例门槛：14 天内至少 3 个不同日期出现相近选择，且没有明显反例。该门槛只是初始产品参数，后续按误报情况调整，不宣称统计结论必然正确。

询问示例：“铭哥，最近你三次把健身改到了晚上。以后优先给健身推荐晚间吗？”选项：采用／仅这次／先不要。

默认每天最多一次主动习惯提议，可关闭。用户拒绝后，同类建议冷却 30 天；没有新证据不反复询问。

### 更新、衰减与遗忘

- 新的明确指令可覆盖旧偏好，并留下可撤销记录。
- 有适用期限的记忆到期失效；“这周忙”不会变成永久偏好。
- 观察候选长期无新证据时降低权重；明确偏好不能仅因缺少活动记录而删除。
- 过去多次偏好与近期变化矛盾时，提出一次具体问题，不自行判断用户生活已经改变。
- 用户可以查看来源、修改、停用、删除、一键清空习惯数据。
- 关闭习惯学习停止新观察；另设“停止使用已有习惯”和“清空学习数据”，含义分明。

## 8. 三层智能体结构

从零构建以代码解耦为硬约束，详细模块依赖见 `architecture.md`。事项、智能体、资料与习惯、闹钟、桌宠和 UI 各有边界，手动输入与智能体操作共用业务用例。

### 角色与对话层

负责 GPT 娘语气、上下文承接、必要追问和可理解的结果解释。

### 理解与检索层

将指令识别为新增、查询、改期、提醒、闹钟、备忘或记忆更新。检索相关事项、有效资料和已确认偏好，生成结构化操作。

### 本地执行层

处理日期转换、事项 ID、目标版本、重复规则、提醒权限、闹钟调度、去重、撤销和错误状态。模型不能绕过该层直接改数据库。

闹钟不依赖模型在后台运行。AI 网络失败时，既有闹钟继续按系统调度；手动记录、日历和备忘仍可使用。

## 9. 较弱模型的适配

详尽预设与程序约束一起使用，不能仅靠增加提示词长度。

1. 固定意图、字段与工具名称，避免开放式“你自己规划”。
2. 一次输出一个 JSON 决策：回复、提问或工具调用。
3. 每次只给当前任务所需的上下文，不把整个资料库塞进提示词。
4. 未知字段允许缺省，不让模型为凑齐 JSON 猜时间、时长或 ID。
5. 本地先校验，再执行；失败返回具体原因，模型修正后再试。
6. 待追问草稿与已确认操作由程序保存，不依赖模型记住完整聊天。
7. 用成功示例、含糊示例和错误恢复示例约束行为。
8. 格式失败有限重试，之后回到手动表单并保留用户原文。
9. 能处理的普通日期表达由程序解析；复杂语义才交给模型。
10. 动画由程序按状态驱动，不需要模型额外生成表情标签。
11. 更换模型通过适配器完成，提示词、领域模型、数据库实体和角色素材分别维护。

## 10. 手机端角色与桌宠

主角为 GPT 娘。视觉采用银白、青绿与浅紫，便签卡片、日期章和少量贴纸。角色在待机、思考、追问、等待、成功、提醒、失败时切换表情。

首版使用状态图片与轻量动画；后续再加入序列帧或 Live2D。关闭动效不会影响功能。

手机上的角色入口分为三种：

1. 应用内 GPT 娘：无需悬浮窗权限，点击打开输入面板；拖动时避开主要操作区。
2. 桌面小组件：在启动器桌面显示角色、下一件事和快速记录入口，符合 Android 小组件的交互能力。
3. 可选跨应用悬浮宠物：使用 Android 悬浮窗，支持拖动、贴边、点击唤出输入和到点提醒气泡。用户首次开启时再申请对应权限。

悬浮宠物只接收角色区域内的触摸，不遮挡整屏；输入面板关闭后恢复其他应用操作。提供尺寸、透明度、临时隐藏与关闭入口。

屏幕关闭时停止角色动画，锁屏时使用系统通知／闹钟页面；桌宠关闭或其服务被系统回收，不改变系统闹钟的调度。悬浮宠物的后台运行和耗电需要 HyperOS 真机验证。

BongoCat 提供桌面交互参考，仓库也有猫角色的 Live2D 模型及相关桥接；SDK 属外部依赖，Windows 窗口代码不能直接用于 Android。当前不复制其代码或模型，手机端使用自身素材和 Android 悬浮窗能力；按铭哥后续要求，0.3.0 冻结桌宠，不继续 Live2D 工作。

## 11. 闹钟整合

参考青铃的本地音乐、可导入在线曲目的缓存、耳机优先播放、断开处理、重复闹钟、稍后提醒、锁屏响铃和重启恢复。

音频模式、未连接耳机的行为必须清楚显示。权限不足时区分“事项已保存”和“闹钟已成功调度”，不能只返回一个笼统的成功。

音乐选择可以留在闹钟设置页。用户使用既有铃声预设时一句话完成；要求特定但未导入的歌曲时，先指出需要导入，不能假装已经选好。

## 12. 开发顺序

### 阶段一：可靠的 Android 最小闭环

全新视觉、今天／日历／备忘／闹钟、GPT 娘入口、一句话操作、具体追问与草稿恢复、基础音乐闹钟、本地存储、撤销和备份。

先建立独立核心业务与存储／平台接口，再接 UI 和真实模型，不把所有逻辑集中到一个 ViewModel 或页面文件。

同时纳入最小资料库：文本导入、相关片段检索、来源显示，以及可管理的明确偏好。它们属于助手的基础能力，不拖到最后。

### 阶段二：长期使用体验

习惯候选与确认、有效期和版本管理、更丰富的导入格式、语音、小组件、可选悬浮宠物、音乐导入增强，以及 HyperOS 真机长期待机验收。

### 阶段三：手机端打磨

在用户真机上完善低功耗桌宠、角色触摸与输入切换、长对话恢复、资料更新与遗忘、模型切换后的行为一致性，以及备份恢复。以用户日常试用反馈决定是否增加更复杂的角色动画和资料导入能力。

## 13. 验收重点

- 一句话信息明确时能执行，含糊时问到点上。
- 问题回答后能继续，不重复让用户输入。
- 没有证据不编造习惯，没有执行成功不报成功。
- 导入资料能引用来源，过期和矛盾可见。
- 习惯可查看、更正、停用和遗忘。
- 网络失效不影响手动记录与已设置闹钟。
- 更弱模型输出错误时，程序挡住错误操作并保留输入。
- 角色增加陪伴感，同时不遮挡任务和操作。
